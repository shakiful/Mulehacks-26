# Architecture

## Components
- Hosting: root `netlify.toml` builds frontend assets and generates an API-first `/api` proxy before SPA rewrites. `render.yaml` runs FastAPI through `backend.app.deploy` with secure cookie settings, bounded provider timeouts and a single persistent SQLite disk. Fixture previews stay isolated from live data. See `DEPLOYMENT.md`; no endpoint/schema changes or serverless SQLite copies.
- frontend/: React/Vite/Tailwind; one shared API client, category pages, shared cards and forms.
- backend/app/: FastAPI routes → domain services → SQLAlchemy repositories/SQLite.
- backend/app/ai/: provider interfaces for classification, extraction and embedding; validated output and timeouts.
- backend/app/matching/: filtering and category scoring; no LLM decides hard constraints.
- backend/app/security/: text/URL-structure risk assessment; never fetch submitted links.
- backend/tests/: route, matching, provider-validation and security tests.

Proposed module paths are targets, not mandatory replacements for a working existing structure. Keep the current layout where practical.

## Pipeline
Preview understanding → missing-detail questions/follow-up understanding → editable confirmation → post validation/persistence → candidate filtering → embedding generation/cache validation → weighted scoring → reasons → connection request. Embeddings are generated lazily for compatible confirmed posts or with the explicit backfill command; preview and post creation remain usable offline.

No vector database is needed for the small demo dataset. Store embedding vector JSON and provider/model metadata and compare in memory. Never compare embeddings from different models or dimensions; regenerate or use a labeled heuristic fallback.

## Data model
- User: id, name, major, created_at; public post authors expose only id/name.
- StudentAccount: user_id, unique username, salted password_hash, active. Only Rafi and Afsana are provisioned for local sign-in; registration and university verification are deferred.
- AuthSession: SHA-256 token_hash (primary key), user_id, csrf_token, expires_at, created_at. The raw session token exists only in an HttpOnly cookie.
- Post: id, user_id, category, intent, title, text, status, location, starts_at, ends_at, category details JSON, created_at, updated_at.
- PostEmbedding: post_id (primary key), provider, model, dimensions, input_version, input_hash, vector, created_at. One current vector per post; incompatible/stale metadata requires regeneration.
- Connection: id, requester_id, receiver_id, source_post_id, target_post_id, status, created_at, updated_at. Unique active pair prevents duplicate pending/accepted requests.
- PostJoin: one target post, requester/receiver, category/intent snapshots, status, requested/reserved seats, timestamps. Unique active post/requester pair; no counterpart post required. Accepted direct seats and matched reservations share capacity accounting and SQLite write locking.
- Message: exactly one Connection or PostJoin parent, session-derived sender, bounded plain text, UTC timestamp. Participant and ACCEPTED checks protect every read/write; cursor pages are always scoped to the thread. Additive tables preserve existing posts, accounts and connections. Shared API adapters and a protected conversation page serve both thread types with polling. Send/read serialization computes an ephemeral SecurityResult with HeuristicSecurityProvider and chat-specific limitations; all historical pages receive the same private checks, independently of Gemini/fallback settings. No new table, analysis column, link fetch or automatic provider call. MessageSafety shows MEDIUM/HIGH advice and offers an explicitly submitted, editable one-message review through the existing security API. The provider receives only selected text; results remain in the viewer's mounted component and clear on edit/close/navigation/account change. An AI response never replaces the automatic warning. No external messaging provider.
- Notification: recipient, public actor, event kind, title snapshot, one join/connection parent, optional unique message ID, created/read timestamps. Created atomically with successful message/request/acceptance events, without private text previews or historical backfill. Recipient-scoped pagination/counts/read watermarks protect privacy and new arrivals. Header polling and in-app alerts share the existing API client; conversation reads acknowledge displayed messages only. The additive table preserves existing records.
- Security analyses: do not persist submitted text in MVP. Return results directly; avoid logging private content.

For speed, use a validated category-specific JSON details column. Separate RideDetails/StudyDetails/FoodDetails tables from the source plan are an optional later normalization. Pydantic validation is mandatory either way. Matches are derived at query time; persisted Match records are deferred to avoid stale scores.

## Matching
Always exclude self, same author's posts, non-OPEN posts, other categories and incompatible intents. Ride additionally requires explicitly confirmed origin_point/destination_point coordinates, pickup and destination distances <=5 km each, departures within 60 minutes, an unbooked REQUEST and remaining offered seats >= requested seats. Text labels are descriptive and need not match; backend matching uses only confirmed coordinates, never guesses them from text. Distances use Haversine with Earth radius 6371.0088 km and remain straight-line measurements, not road routing.

Study score: semantic 0.40 + course/topic 0.25 + availability 0.20 + mode/location 0.15. Semantic component = clamp cosine similarity into [0,1]. Known overlapping availability scores 1, incompatible availability scores 0; two known disjoint intervals are excluded. Missing availability contributes 0, with a missing-data explanation. Course/topic uses normalized token overlap; documented semantic relevance can connect SQL to relational databases even without exact course names. Same known mode scores 1; incompatible known modes are excluded. IN_PERSON requires matching known location; missing location contributes 0.

Ride score: pickup proximity 0.25 + destination proximity 0.25 + time proximity 0.35 + capacity 0.15. Each distance term is max(0, 1-distance_km/5); capacity is 1 after the remaining-seat gate; time = max(0, 1-absolute_minutes/60). Food/Community score: semantic 0.50 + activity/subcategory relevance 0.25 + time/location compatibility 0.25. Unknown data scores 0; do not inflate by removing its weight. Return round(100 * weighted_sum, 1). Sort descending, break ties by target post id. Explanations come from actual score evidence.

RideReservation stores connection_id (primary key), unique request_post_id, indexed offer_post_id and requested seats as an immutable snapshot. Startup creates the additive table and idempotently backfills historical accepted rides without changing posts/connections. A SQLite BEGIN IMMEDIATE write transaction re-reads capacity and roles before acceptance, so concurrent passengers cannot take the same remaining seats. Request completion, reservation insertion, connection acceptance and offer completion when full commit together. Pending requests reserve nothing. Closing an offer early uses existing COMPLETED status; no new enum is needed. Accepted reservations remain terminal in this prototype. Seed refresh skips Ride offers with accepted connections, retaining bookings; repeated seed adds missing pins only to labeled synthetic seed rides.

The shared CreatePost defaults to RidePlaceField From/To comboboxes. The map stays hidden and MapLibre worker/CSS loads only after Show map (optional). Both intents require valid points, supplied by automatic resolution of extracted locations or explicit suggestion/map/Choose map center selection. Campus centering does not count as a pickup. AI extracts labels/logistics, never coordinates. Manual selections survive sentence follow-ups. The optional map uses MapTiler hybrid-v4 satellite/labels and base-v4 streets with VITE_MAPTILER_API_KEY, or OpenFreeMap Bright on no key/load/auth/quota failure. No GPS permission is requested. Form/card route summaries and backend match reasons use miles; internal gates/score formulas retain km and convert with 1 mile = 1.609344 km.

RideLocationHint runs within each From/To field only for untouched extracted labels without existing pins, once per hint/retry. resolveRidePlace validates MapTiler names, coordinates, type and relevance: an exact detailed name/address with relevance >=0.9 and one distinct physical location may auto-fill. City-only, fuzzy, missing-metadata or multi-branch results require selection. UCM/campus and unspecified Walmart aliases query Warrensburg; other unqualified results must be within 25 miles of UCM to auto-fill, while explicit city qualifiers can resolve distant trips. Duplicate layers within 0.02 miles are treated as the same location. “Here” and personal home/dorm references never assume coordinates. Each field cancels stale/disabled requests independently; functional form guards prevent overwriting manual edits. Sentence follow-ups clear previous automatic pins when extracted labels change, including heuristic updates, then resolve the new names. Existing saved/reserved routes are not automatically resolved or rewritten. Final Confirm & post still performs required-field validation and persists only the reviewed values.

The frontend places service uses fixed-host MapTiler forward/reverse geocoding, separate from backend AI. Field suggestions use autocomplete=true with POI/address/road types, a three-character minimum and 400 ms debounce; city-only or invalid-coordinate results are excluded. From is biased around UCM; To around the selected From, without restricting distant city-qualified results. Each field cancels on query change, blur, selection, disabling or unmount; abort/stale guards prevent late results overwriting current state. Accessible listbox/combobox keyboard selection never submits the enclosing form. Selected names and coordinates update atomically. Editing a suggested name invalidates its point immediately; an explicitly clicked unnamed map point can receive a manual name if lookup fails. Reserved offers lock fields/map, preserving backend booking protections. Optional map search retains explicit button/Enter lookup; clicked pins retain their exact coordinates during reverse naming. Transport has an eight-second timeout, bounded validated results and redacted errors. Legacy unnamed points can reverse-resolve without opening the map or saving. Searches are disclosed as sent to MapTiler; confirmed locations remain public in the local demo. Shared form edits are necessary for the requested workflow; no new dependency, backend endpoint or JSON field.

Implemented Food/Community rules: opposite REQUEST/OFFER intents, or Community PARTNER/PARTNER; matching Food activity_type or Community subcategory is a hard gate. Two complete known disjoint intervals are excluded. Food relevance = 0.5 for the same activity + 0.5 times the maximum normalized token overlap of restaurant or cuisine; Community relevance = 1 after the subcategory gate. The time/location component averages time and location with equal weights. Time = 1 for two known overlapping complete intervals; otherwise two known start times use max(0, 1 - absolute_minutes/60); an unknown start contributes 0. Location = 1 for equal normalized nonempty locations, otherwise 0. group_size is descriptive and never treated as reservable capacity.

Fallback mode replaces semantic similarity with deterministic normalized token overlap; label `HEURISTIC`. Semantic mode is `SEMANTIC`. Do not describe fallback as embedding-based.

Heuristic text ranking uses Jaccard overlap after removing common filler words; semantic ranking substitutes validated cosine similarity for that text component. Confirmed Study mode/location/course/time and other category weights remain unchanged. Ride always uses deterministic pin-distance/time/remaining-seat scoring. Understanding remains behind a validated server provider interface. Connection active-pair uniqueness covers PENDING/ACCEPTED in either direction; transitions remain terminal after PENDING. The additive reservation table leaves existing user/post/connection data intact.

Embedding settings are independent of understanding: EMBEDDING_PROVIDER defaults to Gemini (gemini-embedding-001, 768 dimensions), with explicit OpenAI or heuristic alternatives. Selecting OpenAI without model/dimension overrides uses text-embedding-3-small and 1536 dimensions. The input format title-text-v1 is confirmed title + newline + text, hashed with SHA-256. Gemini uses SEMANTIC_SIMILARITY; its input version additionally records gemini-semantic-similarity-v1. A cache row is reusable only when provider/model/dimensions/input version/hash all agree and its vector is finite, nonzero, and the expected length. All required vectors are validated before any regeneration is committed. SQLite upserts make repeated backfills and concurrent writes safe; cache version checks prevent comparing mixed spaces. Model/dimension/input changes regenerate rows. A provider failure makes the entire candidate set HEURISTIC with a warning or raises a standard 503 when fallback is disabled, without overwriting old rows. Ride and empty candidate sets never call providers. Provider HTTP responses are bounded, validated, and not logged; redirects are rejected. Embedding values/metadata stay out of API responses.

AI_PROVIDER defaults to gemini and uses AI_MODEL (default gemini-3.5-flash-lite), AI_TIMEOUT_SECONDS and GEMINI_API_KEY (GOOGLE_API_KEY is an alternative). Every request tries the configured provider; a previous fallback does not disable later Gemini attempts. It sends validated text/reference_time/timezone/category_hint as untrusted data beneath a fixed system instruction, without tools or URL fetching. Its JSON schema is separate from public responses: the server restores original text, computes missing_fields, validates category details, rejects cross-category values, and labels valid output LLM. Word-number clocks and explicit ranges are recognized; missing clocks/dates and recognized ambiguous AM/PM or DST times require clarification. Unsupported output follows the fallback/503 policy. Previews are not stored or embedded. Synthetic live calls verified Google extraction and 768-dimensional semantic vectors; offline automated checks use fakes.

The shared CreatePost form derives focused questions from its current editable values, hiding questions once answered and asking for Study location only for IN_PERSON mode. A follow-up appends the user's sentence to the description and calls the existing understanding endpoint with the original reference_time/timezone and selected category hint. Valid Gemini results update untouched fields; manual corrections win. Heuristic fallback only fills known values so it cannot erase an existing valid draft. Fields and confirmation are disabled while refining, errors preserve the answer/draft, and posting always requires explicit confirmation. No contract fields, provider calls in the browser, or conversation storage were added. Frontend fixtures require VITE_USE_MOCKS=true; live API mode is the default.

## Operational choices
Food Connect's **Check dining menu** button opens a dedicated DiningMenus component beside the existing Create a post control. It uses the shared typed client and UI states; it leaves an open post draft intact. Today's Todd/Ellis menus display as separate hall cards with expandable meal sections, station names and plain-text items. An open panel detects midnight in America/Chicago and reloads the new campus date. Mock mode clearly labels fixed synthetic examples; it has empty/error scenarios and does not contact Sodexo.

`GET /api/dining/menus` calls DiningService without identity or database dependencies. The service computes the actual campus date independently of seed dates/AI settings and reads the public menu feed used by [Todd](https://ucmo.sodexomyway.com/en-us/locations/todd-dining-center-in-todd-hall) and [Ellis](https://ucmo.sodexomyway.com/en-us/locations/ellis-dining-center). Verified on 2026-10-04: API location/menu IDs are Todd 10420009/1410786 and Ellis 10420003/1410907. The official website's public browser header is discovered from its production bundle at runtime and kept only in memory; no dining credential needs local configuration or is committed. Fixed HTTPS hosts, restricted bundle paths, rejected redirects, eight-second HTTP timeouts and bounded responses prevent arbitrary fetching. Nothing from a post or Security submission enters the fetch URLs.

The two halls load independently in parallel. Response normalization drops nutrition/provider internals, empty stations and duplicate item names. Missing listings are EMPTY; fetch/configuration/format failures are UNAVAILABLE, with official links and retry controls. Successful complete responses stay in memory for up to five minutes, keyed by campus date. Failures retry on the next request, and expired or previous-day data is never shown as current. The upstream website/API is an external dependency; if its identifiers or public configuration change, update the adapter. Gemini and the database are not involved.

Private security assessment uses POST /api/security/analyze, SecurityInput (1–8000 characters) and the existing SecurityResult contract. CurrentUser checks the student session and CSRF token; the analyzer itself has no database dependency or writes. SecurityService selects Gemini by AI_PROVIDER with the same server-only key, model and timeout as preview understanding. Its structured response contains only LOW/MEDIUM/HIGH and supported evidence codes/snippets. Snippets must occur in the input; URL-related reasons are also checked against offline parsing. The server owns descriptions, recommendations and limitations, preventing model-generated action links or safety/ownership guarantees. No submitted text, provider response or error contents are logged. Successful API results use Cache-Control: no-store. No links, DNS or URL reputations are queried; only the fixed Google model endpoint receives online text.

The heuristic fallback counts each detected signal once: urgency/reward/IP host/internationalized domain/HTTP score 1; login lure/payment request/user-info obfuscation/script URL score 2; credential request scores 3. Score 0 yields LOW, 1–2 MEDIUM, and 3+ HIGH. Negated credential/payment warnings are excluded. These are prototype risk rules, not calibrated probabilities; Unicode/HTTP/IP alone do not prove phishing. Provider errors or invalid evidence use this labeled HEURISTIC fallback when enabled, otherwise the standard 503. Future requests retry Gemini. Evidence is kept only during validation; public responses use fixed descriptions rather than echoing private text.

SecurityPage uses the existing analyzeSecurity client method, Field/LoadingState/ErrorState/EmptyState and shared layout. The text and assessment exist only in component memory. Editing invalidates stale results; clearing, unmounting and account changes remove the local draft. Generation checks ignore late responses for an earlier account. Submitted links and model text are never rendered as HTML or anchors. Dashboard classification continues to open an empty private workspace, keeping message text out of navigation history. Fixture mode remains explicitly labeled as a canned example. Provider processing is disclosed before submission. No contract, schema table, client adapter or navigation changes were needed.

The October 4 user request authorizes student password sign-in, superseding the original demo identity contract. `/auth/login`, `/auth/session`, and `/auth/logout` are the shared API entry points. Passwords use salted PBKDF2-HMAC-SHA256 with 600,000 iterations following the [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Unknown usernames and incorrect passwords return the same error and perform the same password check; an in-process per-client-IP throttle allows 20 attempts per minute. Rafi/Afsana passwords are supplied only through ignored backend/.env settings and stored hashed in SQLite.

Sessions use random tokens in HttpOnly, SameSite=Lax cookies scoped to `/api`, with a default 12-hour expiry. Token hashes are stored on the server; login rotates the current session and logout revokes it. The browser keeps only the CSRF token in the API client's memory; it does not put credentials or session tokens in localStorage. Protected operations derive the student from the session, and all mutations require the session CSRF token plus an allowed Origin when present. CORS permits configured origins and credentials. Expired sessions return the frontend to `/login`; page reload restores an active session through `/auth/session`. These choices follow [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). Local HTTP uses `SESSION_COOKIE_SECURE=false`; an HTTPS deployment must set it to true. These are local test accounts, without university SSO or verified enrollment.

Startup creates the account/session tables and removes SQLite's legacy `users.is_demo` column. The legacy Rafi id 1 is retained; the old Sarah id 2 becomes Afsana so post/connection ids and ownership links remain valid. Other historical authors may remain solely to preserve their existing records; they are not login accounts or selectable profiles. No old demo-user endpoint, accepted demo identity header, or demo-mode switch remains. Fresh seeding creates only the two account profiles and six labeled synthetic posts. `--reset-passwords` explicitly updates stored hashes from local settings; normal startup/seeding does not change existing passwords.

Use UTC in database; request timezone and reference_time for relative-language extraction. Return ISO 8601 timestamps with offsets, not ambiguous strings. DST ambiguity or missing dates triggers clarification.

The shared form uses separate native date/time controls for start and optional end availability. `lib/dateTime.ts` interprets their wall-clock values in America/Chicago, independently of browser timezone, and converts them to contracted aware timestamps. The backend's existing UTCDateTime converts/stores UTC. AI previews and saved posts round-trip into the campus date/time; manual corrections remain protected during follow-up extraction. Untouched timestamps preserve their original instant and seconds. Missing halves, invalid end ordering and skipped spring times block saving; repeated autumn times require an occurrence choice. Dashboard understanding and post cards also use the campus timezone.

CORS allows only configured frontend origins. Provider credentials stay on the server. Limit input length, validate provider JSON, use timeouts and redact content from logs. Tests inject a fake provider; they never require paid API calls.

Ride saved-post edits acquire the same BEGIN IMMEDIATE lock as acceptance, then reload ownership, state and reservations. Accepted request seat counts are immutable snapshots. Booked requests cannot edit; reserved offers keep their route labels/pins, type and times. Capacity cannot fall below reservations; equaling them completes the offer, while increasing it safely changes remaining capacity. Other category editing remains unchanged. Legacy unbooked rides can select pins in the existing editor without a database reset.
